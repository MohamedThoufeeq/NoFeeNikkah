# NoFeeNikkah API contract

This directory contains the machine-readable OpenAPI contract for the
NoFeeNikkah backend.

| File | Purpose |
| --- | --- |
| [`openapi.yaml`](./openapi.yaml) | OpenAPI 3.0.3 specification with request/response schemas, examples and endpoint descriptions |
| `README.md` | Human-readable explanation of the contract, conventions and maintenance workflow |

The implementation remains the source of truth. The specification is written
against the current Express routes, Zod validators, presenters and SQL search
function, and should be updated in the same change as any API behaviour.

---

## View and validate

Validate the contract with Redocly:

```bash
npx --yes @redocly/cli@latest lint server/openapi/openapi.yaml
```

Render interactive documentation locally:

```bash
npx --yes @redocly/cli@latest preview-docs server/openapi/openapi.yaml
```

You can also import `server/openapi/openapi.yaml` into Swagger Editor,
Postman, Insomnia, Stoplight or any OpenAPI 3.0-compatible generator.

The spec validates with **zero errors**. The remaining Redocly warnings are
intentional and limited to:

- the local development server URL (`http://localhost:8080`);
- health probes having no meaningful `4XX` response;
- a proprietary project without a public license URL.

## Authentication

Protected operations accept either credential:

1. **HTTP-only cookie** — `nfn_session` by default. It is set by register,
   login and social sign-in, and cleared by logout, logout-all and account
   deletion.
2. **Bearer token** — `Authorization: Bearer <opaque-session-token>`. The token
   is also returned in the login/register/social response for mobile and legacy
   clients.

The session token is generated by this API, stored only as a SHA-256 hash in
the `sessions` table, and is **not** a Supabase access token or a JWT. Supabase
refresh tokens are never stored or returned by the application session layer.

`GET /api/profiles/{id}`, `/api/filter` and `/api/search` accept an optional
session:

- guests see public profiles only;
- signed-in users see their own private profile and unmasked contact numbers;
- signed-in users are excluded from their own search results;
- an invalid supplied token returns `401` rather than silently falling back to
  guest mode.

The browser OAuth flow is:

```text
Supabase OAuth redirect
  → /auth/callback receives a Supabase access token
  → POST /api/auth/social { accessToken }
  → API verifies the token, ensures a profile, creates an application session
  → API sets nfn_session and returns the opaque token
```

## Response envelope

Successful responses always use:

```json
{ "success": true, "data": {} }
```

Errors use:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed.",
    "details": [
      { "path": "email", "message": "Enter a valid email address." }
    ]
  },
  "requestId": "9e4f8f7e-2b1d-4a9f-8f0b-3a7c1d2e4f56"
}
```

Every response carries `X-Request-Id`. Clients may send their own matching
`X-Request-Id` (letters, numbers, `.`, `_`, `-`, up to 128 characters) for log
correlation.

| Status | Typical code | Meaning |
| --- | --- | --- |
| `400` | `BAD_REQUEST`, `INVALID_JSON` | Invalid request state or malformed JSON |
| `401` | `UNAUTHORIZED`, `AUTH_ERROR` | Missing, expired or invalid session/credentials |
| `403` | `FORBIDDEN`, `CORS_NOT_ALLOWED` | Authenticated but not allowed, or blocked origin |
| `404` | `NOT_FOUND` | Missing resource, or a private profile hidden from the caller |
| `409` | `CONFLICT` | Duplicate username, email or interest |
| `413` | `PAYLOAD_TOO_LARGE` | Body exceeds `BODY_LIMIT` |
| `422` | `VALIDATION_ERROR` | Zod request validation failed |
| `429` | `RATE_LIMITED` | Rate-limit window exceeded |
| `500` | `INTERNAL_ERROR` | Unexpected failure (provider/database details stay in logs) |
| `503` | `SERVICE_UNAVAILABLE` | Supabase Auth or readiness dependency unavailable |

Private profiles intentionally return `404` to non-owners so their existence is
not leaked.

## Rate limiting

- Global `/api` limit: `RATE_LIMIT_MAX`, default `300` requests per
  `RATE_LIMIT_WINDOW_MS`, default 15 minutes.
- Authentication limit: `AUTH_RATE_LIMIT_MAX`, default `15` requests per
  window, applied to register/login/social.
- Health probes are excluded from the API rate limiter.
- `RateLimit` and `RateLimit-Policy` headers are emitted by
  `express-rate-limit` using draft-8 standard headers.

The current limiter store is in-memory. Replace it with Redis (or another shared
store) before running multiple API instances.

## Domain notes

### Profile shape

`GET /api/profiles/me`, `PATCH /api/profiles/me`, `PUT /api/profiles/me`,
`GET /api/profiles/{id}` and the legacy update route return the full profile
object. Every field is present:

- unset text fields are empty strings;
- unset numeric fields are `null`;
- unset list fields are empty arrays;
- `age` is computed by the server from `dateOfBirth`.

Contact numbers are unmasked only for the owner. Other members and guests
receive masked values.

### Profile updates

The update schema is intentionally permissive for compatibility with the
existing React client:

- canonical camelCase names and legacy aliases are accepted;
- unknown fields pass validation but are ignored by the domain model;
- `id`, `username` and `email` are read-only and always preserved from the
  authenticated account;
- `PATCH` and `PUT` both merge into the existing profile; omitted fields are
  preserved;
- numeric fields treat `null` or an empty string as “not supplied” and preserve
  the existing value rather than clearing it;
- the legacy aliases are listed in the `x-legacy-aliases` extension on
  `ProfileUpdateRequest`.

### Search

`/api/filter` and `/api/search` call the SQL RPC `search_profiles`:

- only `is_public = true` profiles are returned;
- the authenticated caller is excluded;
- `minAge` and `age` form an inclusive age range (`age` is the maximum age for
  backwards compatibility);
- `income` is a maximum monthly income in INR, inclusive;
- `language` and `occupation` use case-insensitive partial matching inside the
  corresponding arrays;
- location, marital status, sect, education, eating habits, practicing level,
  smoking/drinking and financial status use exact matches;
- `page` defaults to `1`, `limit` defaults to `20` and is capped at `100`;
- search results are summary profiles, not the full profile object.

Existing databases must run [`../sql/002_search_filters.sql`](../sql/002_search_filters.sql)
to add the extended filters to the `search_profiles` RPC. Until then the API
falls back to the original function and applies the new filters in memory.

### Interests

- The sender is always taken from the session.
- Self-interests are rejected.
- Duplicate sender→target interests return `409`.
- New interests start as `pending`.
- Only the recipient can `PATCH` the status to `accepted` or `declined`.
- Only the sender can `DELETE` (withdraw) an interest.
- Interest rows are returned in database shape (`snake_case`) for compatibility
  with the existing client.

### Deletion

- `DELETE /api/profiles/me` deletes only the profile row; the auth account
  remains and a profile can be recreated on the next login.
- `DELETE /api/auth/account` revokes sessions and deletes the Supabase auth
  user, cascading to the profile and interests.

## Keeping the contract in sync

When changing the API:

1. Update the route in `server/src/routes/`.
2. Update the Zod schema in `server/src/validators/`.
3. Update the service/repository behaviour.
4. Update the presenter if the JSON shape changes.
5. Update `server/openapi/openapi.yaml`:
   - path and operation;
   - parameters;
   - request body schema;
   - response schema and examples;
   - `security` and expected errors.
6. Run the Redocly lint command above.
7. Update this README if conventions or endpoint groups change.

### Current limitations

- No live Supabase project is configured in this repository, so the database,
  Auth and OAuth flows are not exercised by CI.
- Rate limiting is in-memory and per-instance.
- Profile images are URLs only; there is no upload endpoint.
- Password-reset UI is not implemented.
- The spec describes the current legacy routes; remove them from both code and
  spec together when the client no longer uses them.
